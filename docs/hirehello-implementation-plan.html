HireHello: make your first hello count.

A web app where a job seeker signs in with Google, connects Gmail, chooses from saved email templates and résumés, enters multiple recruiter contacts, previews each personalized message, and starts sending to all selected recipients with one click. Each recipient gets a separate email from the user's own Gmail account, even if the browser closes after confirmation.

Existing Next.js + TypeScript appVercel Queues + local workerMongoDBSmall-group first release

1. Product scope

Core promise

Prepare one campaign, personalize only the recruiter name and company name, then send individual messages without repeatedly composing the same email.

Primary user

A job seeker with their own Gmail or Google Workspace mailbox and a list of relevant recruiter or hiring manager email addresses.

MVP success

A user can send a small campaign to distinct contacts, see a separate result for each, and avoid accidental repeat sends.

First-release decision: Support fewer than 20 invited users, multiple saved templates and PDF résumés, and one-click sending to multiple user-supplied recruiters. A server-side worker continues the queue after the user closes the tab. The user can reopen HireHello to see progress, failures, and any action needed; notifications can be added later.

2. User journey

Sign in with Google→Connect Gmail→Upload résumé→Create template→Add contacts→Preview and test→Confirm send→Review results

Before sending

  • Show the sender Gmail address clearly.
  • Reject empty or malformed addresses and missing merge fields.
  • Display contact count, duplicates, opt-outs, chosen résumé, and exact subject/body preview.
  • Require explicit confirmation: “Send X individual emails.”

After clicking send

  • Create a campaign snapshot and one delivery record per contact.
  • Queue messages and show live progress as the worker sends.
  • Allow the user to pause unsent items.
  • Keep successes and failures visible, with a safe retry path for known failures.

4. Technical architecture

Browser (Next.js React UI) │ HTTPS; secure session cookie ▼ Next.js Node server (TypeScript) ├── Google OAuth callback + session ├── API route handlers / server services ├── validation + campaign snapshot └── MongoDB: users, templates, contacts, campaigns, deliveries, GridFS PDFs │ atomic job claim ▼ Vercel private queue consumer │ OAuth refresh + MIME PDF attachment ▼ Gmail API users.messages.send

Suggested stack

  • Web: Extend the existing Next.js App Router and TypeScript app; use its current styling approach.
  • Validation: Zod shared between forms and server inputs.
  • Database: MongoDB with the official Node driver; private PDF storage, including an immutable campaign attachment snapshot.
  • Google: Reuse the existing NextAuth sign-in with identity scopes; request only gmail.send when connecting Gmail, and store Gmail refresh tokens only on the server.
  • Worker: A private Vercel Queue callback processes one delivery per invocation. A local Node.js polling worker shares the same processor.

Why a durable queue?

One click starts multiple individual emails. The web request saves the approved campaign and publishes its ID. Vercel invokes a private bounded sender, then retries after a delay while work remains. This continues after the browser closes and needs no paid persistent worker. MongoDB stores the authoritative messages, leases, and pacing state.

Deployment: Next.js + Vercel Queues + managed MongoDB. Local development retains a polling worker.

5. Google sign-in and Gmail authorization

Google account sign-in

Use OpenID Connect openid email profile to identify the user. Validate the ID token on the server and create a secure, HTTP-only application session. Do not treat a Google ID token as permission to send email.

Ask for Gmail access when needed

On “Connect Gmail,” request only https://www.googleapis.com/auth/gmail.send. This is a sensitive scope; a public app generally needs Google OAuth verification. The user should see which mailbox will send.

Server-side authorization code exchange

Use OAuth state and PKCE where supported; exchange the code only on the server. Request access_type=offline so the worker can refresh access tokens while the queue runs. Encrypt the refresh token at rest; never send it to the browser.

Disconnect and reauthorize

Allow token revocation, deletion of stored credentials, and reconnection. If Google rejects a token, pause the user's queue and display “Reconnect Gmail.”

Release gate: Create a Google Cloud project, configure the OAuth consent screen, enable Gmail API, publish a privacy policy, and complete Google's verification for the Gmail send scope before broad public launch. Development can use authorized test users. Check current Google requirements during submission.

8. Reliable sending workflow

Validate and snapshot

At confirmation, recheck the Gmail grant, résumé, template, email syntax, duplicate recipients, opt-outs, and campaign cap. Render all merge fields. Store one delivery row per recipient with the exact text the user approved, and snapshot the selected PDF once for the campaign. Return immediately after saving the queue.

Claim one delivery safely

Worker uses an atomic findOneAndUpdate with a lease to claim a queued row. Limit concurrency to one send per Gmail account initially and pace sends conservatively. User-specific daily limits should be lower than Google's maximum and configurable later.

Build and send individual MIME messages

Use a MIME builder to create text/plain plus the selected PDF attachment, encode as base64url, and call Gmail users.messages.send once per contact. Each message has one To address, not a shared CC/BCC list.

Record outcomes carefully

Store Gmail's message ID and mark accepted by Gmail after a successful API response. For explicit 4xx/429/5xx errors, classify retryable versus permanent and use backoff where appropriate. A timeout after submission is uncertain: do not automatically resend, because Gmail send has no application-level idempotency key.

Pause on account or policy problems

On revoked access, permission denial, or daily send limit, pause that user's remaining queue and show a clear action. A pause request prevents new claims but cannot unsend a message already in flight.

Status language: “Accepted by Gmail” means the API accepted the request. It does not prove inbox delivery or that a recruiter read the email. Reading replies would need additional Gmail scope and a separate product decision.

9. Privacy, deliverability, and abuse controls

Protect user data

  • HTTPS, secure HTTP-only SameSite session cookies, CSRF defense, input validation, and owner checks.
  • Encrypt Gmail refresh tokens with a managed secret/KMS key; keep credentials out of logs and analytics.
  • Private PDFs; file-type and size validation; malware scan if accepting broader file types later.
  • Minimal retention, user export/deletion, and a clear privacy policy.

Respect recipients

  • User imports contacts they have a legitimate reason to approach; no scraped lists in MVP.
  • Send relevant, accurate, individually addressed messages; no misleading subjects or impersonation.
  • Maintain an opt-out/suppression list and prevent repeat outreach to opted-out contacts.
  • Start with small paced campaigns; watch Gmail errors and stop on unusual bounce or limit signals.

Important constraint: Gmail prohibits spam and unsolicited commercial mail, and sending limits apply to both personal and Workspace accounts. The product should make targeted professional outreach easy, not promise unlimited bulk sending. Review applicable email rules in the launch countries before release.

11. Acceptance criteria and test plan

  • User can sign in and connect the same Google mailbox for sending; disconnection stops new sends.
  • User can save two templates, upload two PDFs, and choose one of each for a campaign.
  • CSV import identifies invalid emails, duplicate rows, and suppressed contacts before confirmation.
  • Preview substitutes only supported variables and shows exact subject/body for each recipient.
  • Two valid contacts produce two separate Gmail messages with their own To header and the chosen PDF.
  • Double-click or repeated network submission creates one campaign via an idempotency key.
  • Worker restart resumes queued work; an uncertain send result is held for review rather than resent.
  • After campaign confirmation, closing the browser does not stop queued sends; reopening the app shows current results.
  • Pause prevents unsent deliveries from being claimed; in-flight behavior is explained in the UI.
  • Another signed-in user cannot read the first user's contacts, résumé, template, token, or campaign.
  • Rate-limit, revoked-token, oversized-PDF, and Gmail-error paths display actionable states.

Test mix: unit tests for CSV parsing and template rendering; API integration tests for ownership, idempotency and campaign snapshots; worker tests with a Gmail API stub for success, 429, token revocation and ambiguous timeout; one small live end-to-end send using test accounts.

12. Backend architecture guide

This section describes the code that now exists, including the reason for each component and the path a campaign takes through the system. Sections 1–11 remain the product plan. The implementation is a small-group MVP; live Google consent, a real MongoDB instance, deployment, and public OAuth verification still require environment setup.

12.1 Processes and responsibilities

React dashboard→Next.js API routes→MongoDB + private GridFS PDFs→private Vercel queue consumer→Gmail API

Next.js web process

app/dashboard/page.tsx calls routes under app/api. These routes authenticate the request, validate inputs, apply ownership checks, and save durable data. The send button returns after queue creation; it does not hold an HTTP request open while Gmail sends every message. This keeps the interface responsive and lets sending continue after the browser closes.

Shared sender

worker/processor.ts handles one account and at most one send per invocation. Production calls it from the private Vercel Queues route; worker/index.ts polls locally. A database lease serializes each sender even across cold starts or duplicate callbacks. This permits parallel users while keeping an individual account paced.

MongoDB

lib/db.ts opens one reusable client and creates indexes. Collections hold user-owned contacts, templates, résumés, grants, campaigns, deliveries, and suppressions. MongoDB is both application storage and the small queue: an atomic row claim prevents two worker iterations from claiming the same delivery.

GridFS

The resumeFiles bucket stores private PDFs in MongoDB chunks. The campaign route copies the chosen file to a new snapshot before exposing queued deliveries to the worker. Editing or deleting a library résumé later cannot silently change an already approved attachment.

12.2 Identity and authorization: why two Google flows?

  1. Sign-in: app/api/auth/[...nextauth]/auth-options.ts uses NextAuth Google sign-in with openid email profile. The JWT session contains the Google subject ID (sub) as session.user.id. The subject is a stable account identifier; email addresses can change. The browser session has no Gmail access or refresh token.
  2. Gmail connection: GET /api/gmail/connect starts another authorization-code request for gmail.send and offline access. It creates a ten-minute gmail_oauth_attempts record with a hash of a random state value, the PKCE verifier, the signed-in Google subject, and the exact redirect URI. The callback atomically consumes that record once, exchanges the code on the server, validates the Google ID token, requires the same sub as the initiating account, and verifies the send scope. This allows multiple in-progress attempts and does not depend on the browser returning a separate state cookie.
  3. Stored grant: lib/gmail/crypto.ts encrypts the refresh token with AES-256-GCM using a 32-byte key from GMAIL_TOKEN_ENCRYPTION_KEY. The google_grants document stores ciphertext, mailbox address, scopes, and connection status. The worker decrypts only when it needs to refresh an access token. The encryption key must stay outside MongoDB and must be backed up separately.
  4. Disconnect and recovery: DELETE /api/gmail/connection pauses queued campaigns, deletes the local grant, and asks Google to revoke it. A revoked or invalid grant changes to a reconnect-required state and pauses work. Once the same account reconnects, the user can explicitly resume a paused campaign.

Separate consent lets a person explore HireHello before granting sending rights. It also limits the initial sign-in permission. The worker can continue after the browser closes because it holds a server-side refresh grant, not a browser access token.

12.4 Request-to-send walkthrough

Save materials

/api/templates validates plain-text subject/body and a fixed merge-field allowlist. /api/resumes accepts only PDF uploads up to 4 MB, checks the PDF header, hashes the bytes, and stores them privately in GridFS. /api/contacts adds manual rows; /api/contacts/import parses CSV, counts invalid/duplicate/suppressed rows, and stores valid contacts.

Preview

POST /api/campaigns/preview loads only records owned by the session's Google subject. It checks Gmail connection, contact state, suppression and earlier outreach; then substitutes {{recruiterName}}, {{companyName}}, and {{senderName}}. Preview writes no campaign or email.

Test to self

POST /api/campaigns/test renders the chosen template and résumé into one message addressed only to the connected Gmail address. It stores a test-send idempotency key before calling Gmail and limits tests to three in 24 hours. If the Gmail response is lost, it records an uncertain result and asks the user to check Sent Mail.

Confirm and enqueue

POST /api/campaigns repeats the server validation because a preview can become stale. It requires an Idempotency-Key, enforces a small campaign and creation rate limit, copies the PDF, stores each final rendered message, and marks the campaign queued. The API returns the campaign and delivery rows for display.

Claim and send

The worker atomically changes one eligible row from queued to sending with a lease. It rechecks campaign status, Gmail grant, suppression, and the per-account 24-hour cap. It builds a plain-text multipart MIME message with one To address and the PDF snapshot, encodes it base64url, and calls users.messages.send. Default pacing is 15 seconds between claims and 20 accepted or uncertain messages per rolling 24 hours. Uncertain sends count conservatively because Gmail may have accepted them.

Record outcomes

Gmail success stores its message ID and marks the row accepted. Explicit retryable errors are requeued with backoff up to an attempt cap. Credential and send-limit errors pause work. A transport timeout or expired worker lease is uncertain, because Gmail may already have sent the message; it is never automatically resent. The dashboard polls campaign results and supports pause, resume, and retry of known failures.

12.5 Status model and failure decisions

Campaign: preparing → queued → completed ↘ paused → queued (explicit resume) Delivery: queued → sending → accepted | failed | skipped | uncertain ↖ retryable explicit failure / manual retry of failed only

accepted means Gmail accepted the API request, not that the inbox received it. uncertain deliberately blocks automatic retry to prevent duplicate mail after an ambiguous network result. A pause stops new claims; a request already in flight may finish. Campaign counters are reconciled from delivery records after a terminal result and on future callbacks, repairing a crash between result and counter writes.

Automatic contact organization and confirmation dialogs

The Contacts screen opens on Ready to contact. When an email is queued, its address leaves this list immediately. After Gmail accepts the send, the contact appears under Contacted, with the acceptance date and a link to the campaign. Users do not need to delete a person after sending.

ViewAuthoritative conditionEligible for a new campaign?
Ready to contactNo queued, sending, accepted, or uncertain delivery for this owner and normalized address; no suppression.Yes. Known failures and skipped sends remain eligible unless blocked.
ScheduledA queued or sending delivery exists, including a queued delivery in a paused campaign.No; view the existing campaign to manage it.
ContactedGmail accepted the send request. This does not confirm inbox delivery or reading.No.
Needs reviewAn uncertain delivery exists. Gmail may have sent the message even though its response was lost.No; check Gmail Sent. The app does not automatically resend.
BlockedThe contact is suppressed or a suppression record exists for its address.No. Suppression takes precedence over other states.

Why compute outreach state instead of deleting contacts?

lib/core/contact-outreach.ts derives the display state from existing deliveries and suppressions. GET /api/contacts performs two batched, owner-scoped lookups, rather than querying once per person. Delivery lookup uses the existing partial unique index on userId + to. Display eligibility, campaign preparation, and index creation share RESERVED_DELIVERY_STATUSES.

Delivery history is the source of truth. Updating a separate “contacted” flag in the worker would introduce another write that could fail after Gmail already accepted the email. Deriving the status avoids that inconsistency, works immediately for older sends without migration, and preserves protection if a contact is deleted and later reimported with a new ID. Protection applies per user and normalized email address; different email addresses for the same person are not automatically merged.

The browser polls contacts and campaigns every five seconds while work is scheduled, and refreshes outreach when the page regains focus or visibility. Contacts no longer eligible are removed from the draft selection and invalidate its preview. The server still rechecks eligibility during preview and campaign creation, and the database unique index remains the final guard against concurrent campaigns.

Consistent, accessible confirmations

ConfirmDialog replaces browser popups for removing contacts, blocking sends, deleting templates and résumés, disconnecting Gmail, and the final campaign send. It uses a native HTML dialog with custom styling: a descriptive title, an affected-person or material summary, explicit action labels, and a quiet Cancel action. Cancel receives initial focus; Escape dismisses before submission, background interaction is blocked, and focus returns to the trigger. While a request runs, duplicate submission and dismissal are disabled. Errors remain in the dialog for retry.

Removal semantics: removing a contact deletes its address-book entry, not campaign history, and does not cancel queued emails. “Block sends” is the action for preventing future delivery. Completed contacts can simply stay in Contacted.

Verification

Unit checks cover each outcome and suppression precedence. Concurrency and duplicate prevention

A unique sender_locks.userId index permits one lock document per account. An atomic conditional update acquires a 180-second lease, longer than the Vercel function's 120-second lifetime. Its persisted nextSendAt prevents new callbacks or cold starts from resetting the 15-second interval. The rolling cap includes accepted and uncertain sends. Reaching it pauses campaigns for explicit user review and resume.

Each delivery has a separate owner and lease. Before Gmail is called, the processor checks both ownership fences again. Gmail sending has a 30-second timeout and token refresh has a 20-second timeout. If a process dies after sending, an expired delivery is marked uncertain and never automatically resent. This avoids claiming exactly-once email delivery, which Gmail cannot guarantee after a lost response. Repeated queue deliveries safely inspect Mongo state.

Scheduling, retries, and recovery

The callback deliberately returns a delayed retry while more work remains. It does not sleep inside a function or start fire-and-forget work. Queue messages remain available for seven days. Creating a campaign, resuming it, and retrying a known failed delivery all publish a wake message. If Vercel cannot accept that message, the campaign stays saved with a pending scheduling status.

The Campaigns screen offers Restart sending, which calls POST /api/campaigns/:id/dispatch. The route requires a session, same origin, ownership, and a queued campaign; repeated requests are limited to one per 30 seconds. This also recovers work after a prolonged queue outage or message retention expiry. Queued delivery records and PDF snapshots do not expire with queue messages. Paused campaigns still require explicit resume.
